# Aleatoric Music Generator

## Description

This program provides an interface to generate what is known as *aleatoric* music,
which can be most easily described as randomly-generated music that obeys certain
structures and conventions of music theory. In the case of this particular program,
a random tempo and random song key are chosen from a limited set in addition to a
random sequence of commonly-known chord progressions (e.g. I-IV-ii-V) and song 
structures (e.g. AABBCC).

After a loose structure is defined, the melody for the song is then generated by
randomly selecting notes using the chosen key and chord progression. A little bit of
spice is added by having a small chance of picking non-chord notes as part of the
note population process.

Each A/B/C/etc phrase stays the same across all invocations within a single song,
allowing for melodies, verses, and choruses that stay constant to provide more
structure to the song.

## Build

This application uses a cmake build. To build, run:
```
cd ~
mkdir -p build/aleatoric && cd build/aleatoric
cmake <repo location>
make
```

If building from source, you will need to install [PortAudio](https://files.portaudio.com/download.html) and [libsndfile](github.com/libsndfile/libsndfile) if not already installed.
If you're just running the application, you will likely still need PortAudio (I haven't tested this or configured the executable for portability well).

## Run

Running the application without any flags will simply generate a song and play it
to your machine's default audio output device. Using the `--output` flag will save the
song in WAV format (the file is saved before playing, so interrupting the process won't
affect the saving of the file). Additionally, there are a few other flags that provide
bonus features:
```
"usage: ./aleatoric [options]
"  options:
"    --help                 : prints this message
"    --bass                 : adds a bass line to the track
"    --harmony              : enables harmonization for melody notes
"    --output FILENAME.wav  : saves the track to FILENAME.wav
```

## Notes

All the notes in the program's output are generated with sawtooth waves, which can
produce very poor sound quality if their amplitude is too high. The program tries
to lower the default amplitude when harmony or bass are added, but be aware that
VLC or other media players may automatically raise the volume when opening a `.wav`
output from the application, resulting in poor audio degradation and really "crunchy"
layering of sounds.

### Implementation Details

To allow for portability and extension, much of the music data is defined in LUTs
located in `music_tbls.h` or `music_utils.c`. Each 12tet note from C0 through C9
inclusive is given an individual enum value as defined in `music_tbls.h`. This file
also contains a full set of macros that provide the frequency of each note in Hz.
These two are then linked together in a `const float hz_lut[]` table in `music_utils.c`
that allows for easy retrieval of a note's frequency by simply indexing the table
with the enum value.

The individual chord types are also macro'd in `music_tbls.h` as triplets of indices
for the octave notes that are in the chord. This allows for a simple repetition and
addition of four-chord progressions as defined in `const int progressions[][][3]` in
`music_utils.c`.

Outside of the raw music data required to generate the tones and make decisions about
note selection, the entire song is created through a nested series of structs. This
is relatively extendable, although the application is not currently set up well for
arbitrary song length, note depth, time signature, etc.

### Fixes and Improvements

There are a few flags for unimplemented features that would be nice to extend; namely,
the addition of a drum track or randomization of rhythm, as well as the ability to
hook up the program to provide a MIDI out as either a live device or a file of MIDI
messages. Additionally, extending the types of chord progressions, song structures, or
adding support for distinct verse/chorus/bridge structures would be great.

The source code currently should not be terribly hard to modify to extend some of these
features. The primary improvement required would be to switch as much 
statically-allocated structural logic as possible over to dynamic logic to allow
for more complex song structures and better support for arbitrary numbers of notes,
measures, or phrases that can adjust and change with keys or time signatures. In
particular, the current implementation assumes a static eight eighth notes per measure,
with each note struct containing at most three notes, each of which has the same 
length.
